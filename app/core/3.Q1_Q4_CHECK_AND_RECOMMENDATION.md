# Q1~Q4 기능 중복 체크 및 추천

> Q1~Q4에서 물어본 항목이 **core 밖 다른 폴더/파일에 이미 구현돼 있는지** 검사하고,
> 없으면 **필요성·추천**을 정리한 문서.

---

## 1. Q1: orchestration / mcp / utils

### 1.1 orchestration (WorkflowManager, DecisionMaker, 노드·전략)

| 검색 대상 | core 밖 구현 여부 | 사용처 |
|-----------|-------------------|--------|
| WorkflowManager, DecisionMaker, PolicyStrategy, RuleStrategy | **없음** | **app/core/orchestration** 에만 존재 |
| 사용하는 쪽 | - | app/api/v1/minso (feedback, reasoning, submission, training), training/orchestration, tests |

**결론**:
- **같은 기능이 core 밖에 없음.** 오직 `app/core/orchestration` 에만 있음.
- **core에서 제거하거나 밖으로 옮기면** api·training·테스트 전부 import 깨짐.
- **추천**: **core에 그대로 유지 (Q1-A).** “강사 구조 문서에 없어도” 이 프로젝트 전용 워크플로우 레이어로 두는 게 맞음.

---

### 1.2 mcp (MCP 프로토콜·전송)

| 검색 대상 | core 밖 구현 여부 | 사용처 |
|-----------|-------------------|--------|
| MCPProtocol, MCPTransport, MCPRequest/Response | **없음** | **app/core/mcp** 에만 존재 |
| 사용하는 쪽 | - | **test_phase0.py** 만 (프로토콜 테스트). domain/models/bases/reasoning.py 에 MCP 관련 **컬럼 주석**만 있음 |

**결론**:
- **같은 기능이 core 밖에 없음.**
- 실제 API·도메인·training에서는 **MCP를 호출하는 코드가 없음** (테스트 1곳 + 모델 주석만).
- **추천**:
  - **당장 제거할 필요는 없음.** core에 두고, 나중에 MCP 기반 연동을 할 때 그대로 사용 (Q1-A).
  - MCP를 아예 쓰지 않기로 하면, 테스트만 정리하고 core/mcp 는 빈 스텁으로 두거나 제거해도 됨.

---

- **같은 기능이 core 밖에 없음.**
- logger / pdf_parser / test_data_factory 는 api·domain·training·core 전반에서 사용.
- **추천**: **core에 그대로 유지 (Q1-A).** 제거·이동 시 영향이 크므로 유지.

## 2. Q2: ml/ vs llm/ + korean_embeddings + vectorstore

### 2.1 현재 core/ml (ModelLoader, InferenceEngine, KoELECTRALoader)

| 검색 대상 | core 밖 구현 여부 | 사용처 |
|-----------|-------------------|--------|
| ModelLoader, InferenceEngine | **없음** | **app/core/ml** 에만 존재 |
| KoELECTRALoader | **없음** | **app/core/ml** 에만 존재 |
| 사용하는 쪽 | - | app/domain/v1/minso/spokes/reasoning_service, training/services, app/core/orchestration/decision_maker, 테스트 |

**결론**:
- **같은 기능(분류·추론·KoELECTRA)이 core 밖에 없음.**
- **추천**: **ml/ 은 그대로 유지.** 제거하면 reasoning·training·decision_maker 전부 깨짐.

---

### 2.2 강사 구조의 llm/ + korean_embeddings + vectorstore + rag_chain

| 검색 대상 | core 밖 또는 core 안 구현 여부 |
|-----------|-------------------------------|
| ChatOpenAI, create_llm, BaseLanguageModel, init_korean_llm | **프로젝트 전체에 없음** |
| vectorstore, PGVector, create_rag_chain, RAG, Embeddings, init_korean_embeddings | **프로젝트 전체에 없음** (test_langgraph.py 에 "RAG" 문자열만 있고, 실제 구현·import 없음) |
| domain/models/bases/*_embeddings.py | **파일만 있고 내용 비어 있음** |

**결론**:
- **RAG·벡터스토어·채팅용 LLM·한국어 임베딩** 기능은 **프로젝트 어디에도 구현돼 있지 않음.**
- 강사 구조의 `llm/`, `korean_embeddings.py`, `vectorstore.py`, `rag_chain.py` 는 **중복이 아니라 “아직 없는 기능”**을 위한 자리.
- **추천 (Q2)**
  - **지금 당장** RAG·채팅·벡터검색을 쓰지 않으면:
    - **llm/, korean_embeddings, vectorstore, rag_chain** 은 **빈/스텁으로 두고** 두어도 됨 (Q2-B).
    - 나중에 RAG·채팅 도입 시 여기에 구현하면 됨.
  - **ml/** 은 **그대로 유지** (분류·KoELECTRA용).
  - 즉: **강사 구조 추가 + ml 유지 (공존)** 으로 가되, RAG/LLM/vectorstore 구현은 “필요할 때” 해도 됨 (Q2-A + B 혼합).

## 3. Q3: database/connection.py vs 강사 문서의 “session 한 파일”

| 검색 대상 | core 밖 구현 여부 | 사용처 |
|-----------|-------------------|--------|
| get_session, get_database, DatabaseConnection, SessionManager, create_async_engine | **없음** | **app/core/database** (connection.py, session.py) 에만 존재 |
| 사용하는 쪽 | - | app/main, app/api/v1/minso 전부, database/seed_data, test_langgraph_orchestrator, alembic, domain bases, training/models |

**결론**:
- **같은 기능이 core 밖에 없음.** DB 연결·세션은 core/database 에만 있음.
- **추천 (Q3)**
  - **connection.py 는 그대로 두는 것을 추천 (Q3-A).**
  - session이 connection에 의존하고 있고, 사용처가 많아서 **지금** connection을 session에 합치면 변경 범위가 큼.
  - 강사 문서의 “session 한 파일” 구조는 참고만 하고, **현재는 connection + session 분리 유지.**

## 4. Q4: config (Settings vs Pydantic BaseSettings)

| 검색 대상 | core 밖 구현 여부 | 사용처 |
|-----------|-------------------|--------|
| Settings, load_from_env, config | **없음** | **app/core/config.py** 에만 존재 |
| 사용하는 쪽 | - | app/main, database/seed_data, scripts/test_full_flow, core/database/connection, 기타 |

**결론**:
- **같은 기능이 core 밖에 없음.** 설정은 core/config 한 곳만 사용.
- **추천 (Q4)**
  - **당분간 현재 Settings 유지 (Q4-A).**
  - Pydantic BaseSettings 전환은 선택 사항이고, 전환 시 `settings.xxx` 사용처를 한 번에 바꿔야 함.
  - 강사 구조에 맞추려면 나중에 **llm_provider, openai_api_key, local_model_dir** 등 필요한 필드만 추가해도 됨.

## 5. 요약 표

| 항목 | core 밖에 같은 기능 있음? | 추천 |
|------|---------------------------|------|
| **Q1 orchestration** | 없음 (core에만 있음) | **유지 (A).** 제거/이동 시 api·training 전부 깨짐. |
| **Q1 mcp** | 없음 (core에만, 사용처는 테스트 등 소수) | **유지 (A).** MCP 미사용 시 나중에 스텁화·정리 가능. |
| **Q1 utils** | 없음 (core에만 있음) | **유지 (A).** logger/pdf_parser/test_data_factory 전역 사용. |
| **Q2 ml/** | 없음 (core에만 있음) | **유지.** reasoning·training·decision_maker에서 사용. |
| **Q2 llm/ + embeddings + vectorstore + rag** | **어디에도 구현 없음** | **빈/스텁 유지 (B).** RAG·채팅 도입 시 core에 구현. |
| **Q3 database/connection.py** | 없음 (core/database에만 있음) | **유지 (A).** connection + session 분리 유지. |
| **Q4 config (Settings)** | 없음 (core/config에만 있음) | **현재 방식 유지 (A).** 필요 시 필드만 추가. |

## 6. 결론

- **Q1, Q3, Q4**:
  - orchestration, mcp, utils, database/connection, config 모두 **core 밖에 동일 기능이 없음.**
  - **core에서 제거하거나 구조만 바꾸면** 기존 동작이 깨지므로, **그대로 두는 쪽을 추천.**

- **Q2**:
  - **ml/** → 동일 기능이 core 밖에 없음. **유지.**
  - **llm/ + korean_embeddings + vectorstore + rag_chain** → 프로젝트 어디에도 구현이 없음. **중복 아님.**
  - **지금은** 빈/스텁으로 두고, **RAG·채팅·벡터검색을 넣을 때** core에 구현하면 됨.

이 문서는 “같은 기능이 core 외부에 있는지”만 체크하고, 없을 때 “core에서 어떻게 할지” 추천한 내용입니다.
