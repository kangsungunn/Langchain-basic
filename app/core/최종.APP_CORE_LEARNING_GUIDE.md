# app/core 학습 가이드 — 구조·흐름·기능·역할

> **현재** app/core 폴더의 최종 구조를 바탕으로 한 이론 위주 학습용 정리.
> 마이그레이션·정리 과정(1~7, CORE_CLEANUP_SUMMARY)을 반영한 **현재 상태** 설명.

---

## 1. 개요

### 1.1 core의 위치와 원칙

`app/core`는 애플리케이션 **전역 인프라**를 담당하는 레이어다.

- **역할**: 설정, DB, ML 모델 로딩·추론, 공용 유틸, (향후) LLM·RAG·벡터스토어 자리.
- **의존 방향**: `app/api`, `app/domain`, `training` 등이 core를 **사용**한다. core는 **api/domain을 import하지 않는다**는 것이 원칙이다.
- **비즈니스 로직**: core에는 두지 않는다. 오케스트레이션·정책/규칙 판단·MCP 등은 **domain** (`app/domain/v1/minso/hub`)으로 이전된 상태다.

### 1.2 현재 구조에서 빠진 것 (domain으로 이전됨)

- **오케스트레이션** (WorkflowManager, LangGraph, PolicyStrategy, RuleStrategy) → 제거됨. **domain**의 MinsoHub·ReasoningHub가 담당.
- **정책/규칙 판단** (DecisionMaker) → **domain** `hub/decision_maker.py`로 이동. KoELECTRA **로더**만 core/ml에 남음.
- **MCP** (프로토콜·메시지·전송) → **domain** `hub/mcp_central/`로 이동.
- **validators / converters** → 제거됨. 검증은 Pydantic, 변환은 도메인별 처리로 충분하다는 판단.

## 3. 레이어별 역할과 흐름 (이론)

### 3.1 config — 중앙 설정

- **역할**: 환경 변수 기반 설정 한 곳에서 관리. DB, API, ML, 로깅, MCP 등 전역 설정.
- **형태**: `Settings` 클래스 + class 변수 + (선택) `load_from_env()`.
  (강사 구조는 Pydantic BaseSettings 권장; 현재는 class 변수 유지.)
- **의존**: 다른 모듈을 import하지 않아 **순환 의존을 만들지 않음**.
  database, ml, api, main 등이 config를 읽기만 함.
- **흐름**: 앱 기동 시 한 번 로드 → `settings.DATABASE_URL`, `settings.MODEL_PATH` 등으로 전역 사용.

### 3.2 database — DB 인프라

- **역할**: SQLAlchemy 비동기 엔진·세션·Base·믹스인 제공. 도메인 모델은 **core에 두지 않고** domain/training에 둔다.
- **구성**:
  - **connection**: 엔진 생성·싱글톤. `get_database()`, `Base` 노출.
  - **session**: 세션 팩토리·`get_session()` 제너레이터. FastAPI Depends와 함께 사용.
  - **base**: 모든 도메인 모델의 부모가 되는 `DeclarativeBase`.
  - **mixin**: created_at/updated_at, soft delete, status 등 도메인에서 선택 상속.
- **database.py (파일)**: `from app.core.database import ...` 호환용. 실제 진입은 패키지 `database/__init__.py`에서 이루어짐.
- **흐름**:
  `main.py` 또는 lifespan에서 DB 초기화 → API/도메인에서 `get_session` Depends → 서비스/리포지토리가 동일 세션으로 작업.

### 3.3 ml — ML 인프라 (로더·추론)

- **역할**: **인프라만** 담당. 모델 파일 로드, 추론 실행.
  “정책/규칙 판단” 같은 **비즈니스 해석**은 **domain** (DecisionMaker)에서 수행.
- **구성**:
  - **model_loader**: EXAONE 등 생성형 모델 로더 (싱글톤). domain reasoning_service 등에서 사용.
  - **inference**: InferenceEngine. 실제 추론 호출.
  - **koelectra_loader**: KoELECTRA 분류 모델 로더 (싱글톤). **domain**의 DecisionMaker가 import하여 사용.
  - **embeddings**: (미구현) 임베딩 벡터 생성. RAG/벡터검색 도입 시 구현.
- **의존**: config, utils/logger. domain을 import하지 않음.
- **흐름**:
  도메인(ReasoningHub, DecisionMaker 등)이 core/ml에서 로더·엔진만 가져와 사용.

### 3.4 utils — 공용 유틸

- **역할**: 로깅, PDF 파싱, 테스트용 데이터 생성 등 **도메인 중립** 유틸.
- **구성**:
  - **logger**: 전역 로거 (Singleton). API, domain, ml, training 전반에서 사용.
  - **pdf_parser**: PDF → 텍스트/구조 파싱. 학습 데이터·업로드 API에서 사용.
  - **test_data_factory**: 오케스트레이터·분석 테스트용 더미 데이터. 테스트/개발 전용.
- **제거된 것**: validators, converters. 검증은 Pydantic, 변환은 도메인별로 처리하기로 정리됨.
- **흐름**:
  api/domain/training/ml에서 필요 시 `from app.core.utils import get_logger` 등으로만 사용.

### 3.5 llm / korean_embeddings / korean_llm / vectorstore / rag_chain / langsmith_config

- **역할**: 강사 구조에 맞춘 **자리**. RAG·채팅·벡터검색·LangSmith를 **쓰지 않으므로** 현재는 빈 파일 또는 스텁.
- **이론적 위치**:
  - **llm/**: LLM 타입·팩토리·프로바이더(OpenAI, 로컬 EXAONE/MIDM 등). RAG/채팅 시 주입용.
  - **korean_embeddings.py**, **korean_llm.py**: 한국어 임베딩/LLM 초기화 (HF·OpenAI 등 선택).
  - **vectorstore.py**: PGVector 등 벡터스토어 생성. Neon/Postgres 전제.
  - **rag_chain.py**: RAG 체인 생성 (vectorstore + LLM 주입).
  - **langsmith_config.py**: LangChain 추적 설정.
- **흐름**:
  현재는 사용하지 않음. 필요 시 여기에 구현하면 되고, 그때도 “core = 인프라, domain = 비즈니스” 원칙 유지.

## 4. 전체 데이터·제어 흐름 (현재)

### 4.1 API → Domain (core는 인프라만)

1. **HTTP 요청** → `app/api/v1/minso/*.py` 라우터.
2. **세션**: `get_session` (core/database) Depends로 동일 세션 보장.
3. **오케스트레이션**: 라우터가 **domain**의 `MinsoHub`를 호출.
   `hub.process(domain, action, request)`
   → core/orchestration은 없음. domain hub가 진입점.
4. **정책/규칙 판단**: **domain** `DecisionMaker`가 수행.
   필요 시 **core/ml**의 `KoELECTRALoader`만 사용 (인프라).
5. **정책** → domain의 ReasoningHub 등. **규칙** → domain spoke 서비스 직접.
6. **DB/로깅**: 서비스·리포지토리는 core의 `get_session`, `get_logger` 사용.

### 4.2 core 내부 의존 (이론)

- **config**: 최상위. 다른 core 모듈을 import하지 않음.
- **database**: config 사용. connection → session 순서로 사용.
- **ml**: config, utils/logger 사용. domain을 import하지 않음.
- **utils**: logger는 자체, pdf_parser·test_data_factory는 필요 시 logger 사용.
- **llm / vectorstore / rag_chain 등**: (구현 시) config, 필요 시 서로 주입. api/domain은 이들을 **사용**만 함.

## 6. 학습 시 참고할 원칙 정리

1. **core = 인프라**
   설정, DB, ML 로더·추론, 로거, PDF 파싱 등. 비즈니스 규칙·오케스트레이션·정책/규칙 판단은 **domain**에 둔다.

2. **의존 방향**
   api, domain, training → core 사용. core → api/domain 미사용.

3. **DB·세션**
   connection(엔진) + session(세션 팩토리) 분리. 도메인 모델·리포지토리는 domain/training에 두고, Base·mixin만 core에서 가져다 쓴다.

4. **ML**
   core/ml은 “로딩·추론”만. “이 요청은 정책/규칙이다” 같은 판단은 domain(hub/decision_maker)에서 하며, 필요 시 KoELECTRALoader만 core에서 쓴다.

5. **스텁 파일**
   llm, korean_embeddings, korean_llm, vectorstore, rag_chain, langsmith_config는 **자리만** 두고, RAG·채팅·벡터검색 도입 시 구현한다.

6. **제거·이전된 것**
   orchestration, mcp, validators, converters는 core에서 제거·이전되었고, 오케스트레이션·MCP·판단은 domain hub에서 처리한다.
