# Domain Hub에서 정책/규칙 판단 전략

> **목표**: 정책/규칙 판단을 `core/orchestration`이 아닌 **`domain/v1/minso/hub/orchestrators`**에서 수행하도록 구조 변경.
> 나중에 서브도메인 추가 시 각 도메인의 hub가 자동으로 판단하도록.

---

## 1. 왜 이 접근이 좋은가?

### 1.1 관심사 분리

| 레이어 | 역할 | 비즈니스 로직 포함 여부 |
|--------|------|------------------------|
| **core** | 인프라 (DB, 설정, 유틸, ML 모델 로더) | ❌ 비즈니스 로직 없음 |
| **domain** | 비즈니스 로직 (오케스트레이션, 정책/규칙 판단) | ✅ 비즈니스 로직 포함 |

**정책/규칙 판단**은 **"어떤 요청이 복잡한 처리가 필요한지"**를 결정하는 **비즈니스 로직**입니다.
→ **domain에 두는 게 맞습니다.**

### 1.2 확장성

- **현재**: `domain/v1/minso/hub/orchestrators`
- **나중에**: `domain/v1/patent/hub/orchestrators`, `domain/v1/contract/hub/orchestrators` 등
  → 각 서브도메인의 hub가 **자신의 도메인에 맞는 정책/규칙 판단**을 할 수 있음.

### 1.3 단순화

- **현재**: API → core/orchestration → domain hub
- **변경 후**: API → domain hub (직접)
  → 레이어 하나 제거, 더 단순한 구조.

---

## 2. 제안하는 구조

### 2.1 Domain Hub의 역할 확장

**현재 ReasoningHub:**
- 정책 요청만 받아서 처리 (이미 정책인 걸 알고 있음)

**변경 후 Hub (예: MinsoHub 또는 각 도메인별 Hub):**
- **모든 요청**을 받음 (정책인지 규칙인지 모름)
- **KoELECTRA(DecisionMaker)로 정책/규칙 판단**
- **정책** → 자신이 처리 (ReasoningEngine, FeedbackGenerator 등 호출)
- **규칙** → 해당 서비스로 직접 라우팅 (UserAnswerService, TrainingDataService 등)

### 2.2 구조 예시

```
app/domain/v1/minso/hub/orchestrators/
├── __init__.py
├── minso_hub.py          # ← 새로 추가: 모든 요청 진입점, 정책/규칙 판단
├── reasoning_orchestrator.py  # 정책 처리 (기존 유지)
├── feedback_orchestrator.py   # 정책 처리 (나중에 구현)
└── ...
```

**MinsoHub (또는 각 도메인별 Hub):**
```python
class MinsoHub:
    """
    Minso 도메인 Hub (Star 토폴로지 중앙 허브)

    모든 요청을 받아서 정책/규칙을 판단하고 적절히 라우팅.
    """

    def __init__(self, session: AsyncSession):
        self.session = session
        self.decision_maker = DecisionMaker()  # KoELECTRA 판단기
        self.reasoning_hub = ReasoningHub(session)  # 정책 처리용
        # ... 다른 오케스트레이터들

    async def process(
        self,
        domain: str,
        action: str,
        request: Any
    ) -> Any:
        """요청 처리 (정책/규칙 자동 판단)"""
        # 1. 정책/규칙 판단 (KoELECTRA)
        strategy = await self.decision_maker.decide(domain, action, request)

        # 2. 정책이면 → 자신이 처리 (ReasoningHub 등)
        if strategy == "policy":
            return await self._handle_policy(domain, action, request)

        # 3. 규칙이면 → 서비스로 직접 라우팅
        else:
            return await self._handle_rule(domain, action, request)
```

## 3. DecisionMaker 위치

### 옵션 A: domain/hub 안에 두기 (추천)

```
app/domain/v1/minso/hub/
├── orchestrators/
│   ├── minso_hub.py          # DecisionMaker 사용
│   └── ...
└── decision_maker.py         # ← 새로 추가: KoELECTRA 판단 로직
```

**장점:**
- domain이 비즈니스 로직(판단)을 완전히 소유
- core는 인프라만 담당 (KoELECTRALoader는 core/ml에 두고, DecisionMaker는 domain에)

### 옵션 B: domain/shared에 두기

```
app/domain/v1/minso/shared/
├── decision_maker.py         # ← 새로 추가
└── ...
```

**장점:**
- 여러 hub가 공유 가능
- shared = 도메인 공통 비즈니스 로직

## 4. Migration 전략

### Phase 1: DecisionMaker를 domain으로 이동

1. **core/orchestration/decision_maker.py** → **domain/v1/minso/hub/decision_maker.py** (또는 shared)로 복사
2. **KoELECTRALoader**는 core/ml에 그대로 두고, DecisionMaker만 domain에서 import
3. **RULE_BASED_ACTIONS, POLICY_BASED_ACTIONS**는 domain에 맞게 조정

### Phase 2: MinsoHub (또는 각 도메인 Hub) 생성

1. **domain/v1/minso/hub/orchestrators/minso_hub.py** 생성
2. **MinsoHub.process()**에서 DecisionMaker로 판단 → 정책/규칙 분기
3. **정책**: ReasoningHub 등 호출
4. **규칙**: 서비스 직접 호출 (UserAnswerService, TrainingDataService 등)

### Phase 3: API 변경

**현재:**
```python
# API
from app.core.orchestration import WorkflowManager
workflow_manager = WorkflowManager(session)
result = await workflow_manager.process_request(domain, action, request)
```

**변경 후:**
```python
# API
from app.domain.v1.minso.hub.orchestrators.minso_hub import MinsoHub
hub = MinsoHub(session)
result = await hub.process(domain, action, request)
```

### Phase 4: core/orchestration 제거 (또는 최소화)

- **WorkflowManager, LangGraph, strategies, nodes** → 제거 가능
- **DecisionMaker** → domain으로 이동 완료
- **KoELECTRALoader** → core/ml에 유지 (인프라)

## 5. 나중에 서브도메인 추가 시

### 예: patent 서브도메인 추가

```
app/domain/v1/patent/hub/orchestrators/
├── patent_hub.py          # ← patent 전용 Hub
└── ...
```

**PatentHub:**
- **자신의 DecisionMaker** (patent 도메인에 맞는 판단 로직)
- **자신의 정책 오케스트레이터** (patent 전용 처리)
- **자신의 서비스 라우팅** (patent 전용 서비스)

**API:**
```python
# patent 요청
from app.domain.v1.patent.hub.orchestrators.patent_hub import PatentHub
hub = PatentHub(session)
result = await hub.process(domain, action, request)
```

→ **각 서브도메인이 독립적으로 정책/규칙 판단** 가능.

## 6. 장점 요약

| 항목 | 설명 |
|------|------|
| **관심사 분리** | core = 인프라, domain = 비즈니스 로직 |
| **확장성** | 서브도메인마다 독립적인 판단 로직 |
| **단순화** | API → domain hub 직접 (레이어 제거) |
| **유지보수** | 정책/규칙 판단 로직이 domain에 모여있어서 수정 용이 |
| **테스트** | domain hub만 테스트하면 됨 (core/orchestration 의존 없음) |

---

## 7. 결론

**이 접근은 완전히 합리적이고 권장됩니다.**

- ✅ **정책/규칙 판단을 domain hub에서 하는 것** → 비즈니스 로직이 domain에 있으므로 맞음
- ✅ **나중에 서브도메인 추가 시 각 hub가 독립적으로 판단** → 확장성 좋음
- ✅ **core/orchestration 제거 가능** → 구조 단순화

**다음 단계:**
1. DecisionMaker를 domain으로 이동
2. MinsoHub (또는 각 도메인 Hub) 생성
3. API를 domain hub 직접 호출로 변경
4. core/orchestration 제거 또는 최소화

이 문서는 "domain hub에서 정책/규칙 판단" 전략을 정리한 것입니다. 실제 구현은 이 구조를 바탕으로 단계별로 진행하시면 됩니다.
