# 첨삭 점수·피드백 개선 전략

현재 **쟁점 분석 / 논리 평가 / 표현 검토**가 하드코딩·고정 비율에 의존해, 같은 입력에 항상 동일한 점수·피드백이 나오는 문제를 해결하기 위한 단계별 전략입니다.

---

## 1. 현재 상태 요약

| 영역 | 현재 방식 | 문제점 |
|------|-----------|--------|
| **쟁점 분석** | (조건부) KoELECTRA 분류 모델 → class별 coverage 0.3/0.6/0.9 고정, reference_issues를 비율로 잘라서 사용 | 모델 없으면 0.6 고정; 있어도 deterministic이라 같은 입력→같은 결과; **답안 본문 기반 “어떤 문장이 어떤 쟁점”** 매핑 없음 |
| **논리 평가** | **완전 하드코딩** (coherence 0.78, argument_strength 0.72, 고정 weak_points/suggestions) | 답안 내용을 전혀 반영하지 않음 |
| **표현 검토** | **완전 하드코딩** (clarity 0.75, formality 0.88, 고정 issues/improvements) | 답안 내용을 전혀 반영하지 않음 |
| **강점/개선점 문구** | 쟁점·논리·표현 결과를 **템플릿**으로만 조합 | 위 결과가 고정이므로 문구도 항상 동일 |

**이미 있는 자원**: ExaOne(MCP 툴), KoELECTRA 분류 모델, 논점 추출(extract_issues_from_problem), ExaOne `temperature=0.7`(일부 다양성 가능).

---

## 2. 개선 목표

1. **실제 답안 본문을 읽고** 쟁점·논리·표현을 평가한다.
2. **같은 답안이라도** (특히 생성형 LLM 사용 시) 문구가 미세하게라도 달라질 수 있게 한다.
3. 모델/API 실패 시 **기존 더미로 폴백**하여 서비스는 유지한다.
4. 단계별로 배포 가능하도록 **영역별로 나누어** 적용한다.

---

## 3. 단계별 개선 전략

### Phase 1: 논리 평가·표현 검토를 ExaOne 기반으로 전환 (우선권 높음)

**목표**: 고정값 제거, 답안 본문을 ExaOne에 넣어 **실제로 생성한** coherence/clarity, weak_points, improvements를 사용.

**구현 방향**:

1. **MCP 툴 추가** (또는 기존 툴 확장)
   - `exaone_evaluate_logic(problem_text, reference_text, user_answer_text)`
     → 프롬프트: "다음 문제·모범답안·제출답안을 보고 논리 일관성(0~1), 논증 강도(0~1), 약점 2~3개, 개선 제안 2~3개를 **JSON**으로만 출력해주세요."
   - `exaone_review_expression(user_answer_text)`
     → 프롬프트: "다음 법률 답안의 명료성(0~1), 격식성(0~1), 구체적 표현 문제 목록, 개선 제안 목록을 **JSON**으로만 출력해주세요."

2. **출력 형식 고정**
   - LLM 출력을 파싱하기 쉽게 하기 위해:
     - JSON 한 블록만 출력하도록 지시하거나,
     - ````json ... ```` 같은 마크다운 블록으로 감싸도록 지시.
   - 파싱 실패 시 → 기존 더미 값 사용(폴백).

3. **reasoning_service 연동**
   - `evaluate_logic()`:
     - 문제/모범답안/제출답안 텍스트를 준비한 뒤 `call_tool("exaone_evaluate_logic", ...)` 호출.
     - 반환된 JSON에서 `coherence_score`, `argument_strength`, `weak_points`, `suggestions` 추출 → `LogicEvaluationResult` 생성.
   - `review_expression()`:
     - 제출답안 텍스트만 넘겨 `call_tool("exaone_review_expression", ...)` 호출.
     - 반환된 JSON에서 `clarity_score`, `formality_score`, `issues`, `improvements` 추출 → `ExpressionReviewResult` 생성.
   - ExaOne 호출은 이미 `asyncio.to_thread`로 되어 있으므로, 논리/표현 툴만 추가하면 됨.

4. **다양성**
   - ExaOne 파이프라인에 이미 `temperature=0.7`, `do_sample=True`가 있으므로, **동일 입력이라도 호출마다 문구가 조금씩 달라질 수 있음**.

**산출물**:
- `central_mcp_server.py`에 툴 2개 추가.
- `reasoning_service.py`의 `evaluate_logic` / `review_expression`에서 해당 툴 호출 + JSON 파싱 + 폴백.

---

### Phase 2: 쟁점 분석을 답안 본문과 연결

**목표**: “reference_issues를 고정 비율로 자르기”를 줄이고, **제출답안에서 실제로 어떤 쟁점을 다뤘는지** 반영.

**방안 A – 분류 모델 유지 + ExaOne 보조**
- 현재: 분류 class → coverage 0.3/0.6/0.9 → reference_issues를 앞에서 N개만 “파악”, 나머지 “누락”.
- 개선:
  - ExaOne에 **reference_issues 목록 + 제출답안**을 주고,
    "아래 쟁점 목록 중 제출답안에서 **실제로 다룬 쟁점**만 JSON 배열로 나열해주세요" 같은 툴 추가.
  - ExaOne이 반환한 “다룬 쟁점” 목록을 기준으로 `identified_issues` / `missing_issues` 구성.
  - 점수는 `len(identified) / len(reference_issues)` 등으로 계산.
  - 분류 모델은 “전체 품질” 보정용으로만 쓰거나, ExaOne 실패 시 폴백으로 유지.

**방안 B – ExaOne만 사용**
- 모범답안·문제·제출답안만 주고,
  "제출답안이 모범답안의 쟁점을 얼마나 다루었는지, 다룬 쟁점 목록과 누락된 쟁점 목록을 JSON으로 출력해주세요" 형태의 툴 하나로 통합.
- 출력 스키마를 고정해 파싱(identified_issues, missing_issues, coverage_rate 또는 coverage 설명).

**권장**: 먼저 **방안 A**로 ExaOne “답안–쟁점 매핑” 툴을 추가하고, 기존 분류 모델은 폴백/보조로 두면 리스크가 적음.

**산출물**:
- MCP 툴 `exaone_identify_issues_in_answer(reference_issues, user_answer_text)` (또는 방안 B용 통합 툴).
- `analyze_issues()`에서 해당 툴 호출 → 파싱 → `IssueAnalysisResult` 생성, 실패 시 기존 로직 유지.

### Phase 3: 강점/개선점 문구의 다양성 확보

**목표**: UI에 나오는 “강점 / 개선점” 문구가 **모델 출력**을 그대로 쓰도록 해, temperature에 의해 미세하게라도 달라지게 함.

**현재**:
- `_generate_comprehensive_feedback()`에서 `identified_issues`/`missing_issues` 등으로
  `"'xxx' 쟁점을 잘 파악했습니다"`, `"'xxx' 쟁점이 누락되었습니다"` 등 **고정 템플릿**으로만 생성.

**개선**:
- **Option 1**: 논리/표현을 ExaOne으로 바꾼 뒤, ExaOne이 준 `weak_points` / `suggestions` / `improvements` 문장을 **그대로** 강점/개선점에 넣기. (이미 Phase 1에서 생성 내용 사용 가능.)
- **Option 2**: “종합 강점/개선점”을 한 번에 생성하는 MCP 툴 추가.
  - 입력: issue/logic/expression 요약(점수 + identified/missing + weak_points 등).
  - 출력: "강점 3~5개, 개선점 3~5개"를 JSON 배열로.
  - `_generate_comprehensive_feedback()`에서 이 툴 호출 결과를 `strengths` / `weaknesses`에 넣고, 실패 시 기존 템플릿 유지.

Phase 1을 먼저 하면 Option 1만으로도 문구가 모델 기반으로 바뀌고, temperature로 인해 같은 답안이라도 문장이 조금씩 달라질 수 있음.

---

### Phase 4 (선택): 분류 모델에 약간의 확률 반영

**목표**: 쟁점 분석에서 “완전 결정론”을 완화해, 같은 입력이라도 가끔 다른 coverage가 나오게 할 수 있음 (선택 사항).

- 현재 `InferenceEngine.predict()`는 `argmax`만 사용 → 항상 동일 class.
- **선택적 개선**:
  - 분류 **확률**을 반환받아, `coverage_rate`를 `sum(prob[i] * coverage_map[i])`처럼 기대값으로 계산하거나,
  - 일정 확률로 두 번째 후보 클래스를 쓰는 등 **stochastic rounding**을 넣을 수 있음.
- 이건 “미세한 숫자 다양성”용이라, 우선순위는 Phase 1–3보다 낮아도 됨.

## 4. ExaOne 원론적 해결 (첫 추론 지연)

**문제**: ExaOne 첫 추론 시 CUDA 초기화·커널 컴파일 등으로 **5~8분** 걸려, 타임아웃·멈춤처럼 보임. ExaOne을 포기하면 “학습된 모델이 첨삭”이 아니라 더미만 나감.

**해결 방향** (구현 반영):
- **로드 직후 워밍업**: `_load_exaone_model()` 완료 직후 짧은 추론 1회(max_new_tokens=2) 실행. 첫 추론 비용을 로드 단계에서 한 번만 치르고, 이후 실제 분석 호출은 상대적으로 빠르게 동작.
- **ExaOne 분석 타임아웃 10분**: 첫 요청 시 로드+워밍업으로 6~10분 걸릴 수 있으므로 600초로 설정.
- **동시 로드 방지**: `threading.Lock`으로 ExaOne 로드는 한 번에 하나만 수행.

**추가 검토**: 워밍업 후에도 첫 실제 분석이 느리면, 별도 워커 프로세스에서 ExaOne만 로드·서빙하는 구조를 검토할 수 있음.

**사용 시 주의**:
- 분석(analyze-and-feedback) 요청은 **한 번만** 보내고 **최대 10분** 기다리기. "다시 시도하기" 연타 시 두 요청이 동시에 ExaOne을 쓰려 해서 500·멈춤 가능.
- 백엔드는 `--workers 1`로 실행 (ExaOne은 프로세스당 1개만 로드).

**기능 검증(ExaOne 제외)**:
- ExaOne에서 멈추는지, PDF/OCR/나머지 파이프라인 문제인지 구분하려면 **ExaOne을 끄고** 동작을 확인할 수 있음.
- 환경 변수 `SKIP_EXAONE=1` (또는 `true`) 설정 후 서버 재시작 → **reasoning_service**와 **feedback_service** 모두 ExaOne 로드·호출 없이 **PDF 업로드 → OCR → 쟁점 분석(논점 추출) → 논리/표현 더미 → 피드백 생성**까지 진행됨.
- 이때 **분석·피드백이 정상적으로 끝나고** 리뷰 페이지가 뜨면, PDF 읽기·나머지 기능은 정상이고 **문제는 ExaOne 첫 추론 구간**으로 좁혀짐.

## 5-1. 문제점 파악 결과 (SKIP_EXAONE 검증 후)

**검증 결과**: `SKIP_EXAONE=1` 로 실행 시 **리뷰 페이지가 정상적으로 뜸** (200 OK, 종합 피드백 생성 완료 → 응답 반환).

| 구간 | 상태 | 비고 |
|------|------|------|
| PDF 업로드·저장 | 정상 | POST answers/image 201 |
| OCR | 정상 | POST .../ocr 200 |
| 임베딩(Sentence-BERT) | 정상 | UserAnswer·ReasoningTask·Feedback 임베딩 저장 완료 |
| 종합 분석 (쟁점/논리/표현) | 정상 | ExaOne 스킵 시 더미로 완료 |
| 피드백 생성 | 정상 | ExaOne 스킵 시 72.2점·항목 20개 생성 |
| **ExaOne 로드** | 동작 | Loading checkpoint shards 100%, Device set to use cuda:0 까지 진행 |
| **ExaOne 첫 추론(invoke)** | **여기서 멈춤** | 로드 직후 또는 워밍업/첫 invoke 단계에서 완료되지 않음 |

**결론**:
- **PDF 읽기, OCR, 나머지 파이프라인, API 응답** — 문제 없음.
- **문제는 ExaOne을 켰을 때만 발생**: ExaOne **첫 추론**이 끝나지 않고 멈추는 구간이 원인. (스레드에서 CUDA 추론 시 데드락·극심한 지연, 또는 transformers/CUDA 조합 이슈 가능성.)

**다음 검토 방향**:
- ExaOne 첫 추론을 **메인 스레드**에서 한 번만 실행해 보기 → 완료되면 스레드+CUDA 이슈로 좁혀짐.
- 또는 ExaOne만 **별도 프로세스**에서 로드·서빙하고 API는 그 프로세스에 요청만 보내는 구조 검토.

**적용 완료 (옵션 A)**
`central_mcp_server.py`에서 ExaOne 툴(`exaone_*`) 호출 시 `asyncio.to_thread` 대신 **이벤트 루프(메인 스레드)에서 직접 실행**하도록 변경함.
- ExaOne 툴 실행 중에는 해당 요청이 끝날 때까지 서버가 블로킹되며, 첫 추론이 정상 완료되는지 확인할 수 있음.
- 테스트 시 `SKIP_EXAONE`을 설정하지 않고(또는 0으로) 실행한 뒤 종합 분석을 한 번 요청해 보면 됨.

**옵션 A 테스트 결과 (메인 스레드)**
- 메인 스레드에서 실행해도 **첫 추론(워밍업 또는 첫 툴 invoke) 단계에서 동일하게 멈춤**.
- 로그: `Device set to use cuda:0` → `generation flags...` 까지 출력 후 진행 없음 → **첫 CUDA 생성(forward/decoding) 단계에서 멈춤**으로 판단.
- **결론**: 원인은 스레드가 아니라 **ExaOne(transformers)+CUDA 첫 추론** 구간. 다음 단계로 **옵션 B(ExaOne 전용 프로세스)** 로 분리하는 것을 권장.

**옵션 B 적용 (ExaOne 전용 워커 프로세스)**
- **원인 정리**: uvicorn(FastAPI)과 같은 프로세스에서 **첫 번째 큰 CUDA 작업**(모델 로드·이동·파이프라인 생성·첫 추론 등)이 일어날 때 멈춤. 경로를 바꿀 때마다 멈추는 위치만 바뀌었음.
- **대응**: ExaOne을 **별도 프로세스**에서만 로드·추론하고, 메인 API는 HTTP로 그 워커만 호출.
- **사용법**
  1. 터미널 1: `.\run_exaone_worker.ps1` (또는 `python scripts/exaone_worker.py`)
  2. 터미널 2: `$env:EXAONE_WORKER_URL = "http://127.0.0.1:8765"` 후 `.\run_backend.ps1`
- **설정**: `EXAONE_WORKER_URL` 이 설정되면 메인 앱은 ExaOne을 로드하지 않고, 해당 URL의 `/generate` 로만 요청을 보냄. 워커는 `scripts/exaone_worker.py` 로 단일 프로세스에서 모델 1회 로드 후 HTTP 서빙.

## 6. 구현 시 유의사항

| 항목 | 내용 |
|------|------|
| **타임아웃** | ExaOne 호출이 길어지므로, MCP 툴 또는 `call_tool` 쪽에 타임아웃(예: 120초)을 두고, 초과 시 폴백. |
| **출력 파싱** | JSON 파싱 실패·필드 누락 시 반드시 기존 더미 또는 이전 단계 결과로 폴백. |
| **로그** | `meta["model"]`, `meta["dummy"]`로 “실제 ExaOne 사용 여부”를 구분해 두면, 운영 중 점유율·폴백률 파악에 유리. |
| **비용/지연** | 논리+표현+쟁점을 모두 ExaOne으로 하면 호출 횟수·시간이 늘어남. 필요 시 배치(한 번에 긴 프롬프트로 여러 항목 요청) 검토. |

## 7. 권장 진행 순서

1. **Phase 1**
   - 논리 평가·표현 검토를 ExaOne 툴 + JSON 파싱 + reasoning_service 연동으로 전환.
   - 같은 답안을 여러 번 넣어서 문구·점수가 조금씩 달라지는지 확인.

2. **Phase 2**
   - 쟁점 분석에 ExaOne “답안–쟁점 매핑” 툴 도입(방안 A 우선).
