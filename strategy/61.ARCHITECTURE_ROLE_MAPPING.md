# 🔍 강사님 구조 vs 현재 프로젝트 역할 매핑

## 📋 목적

강사님의 축구 도메인 예제 구조와 현재 프로젝트(민사소송법 답안지 첨삭 시스템)의 역할을 비교하여, LangGraph 전환 전략이 올바르게 적용될 수 있는지 확인

**중요**: 폴더/파일 이름은 다를 수 있으므로, **역할과 의도**만 비교

## 🎯 강사님 구조 (축구 도메인 예제)

### 구조 개요
```
app/domain/v10/soccer/
├── hub/
│   ├── orchestrators/          # Strategy Pattern 기반 오케스트레이터
│   │   ├── player_orchestrator.py
│   │   ├── team_orchestrator.py
│   │   ├── stadium_orchestrator.py
│   │   └── schedule_orchestrator.py
│   └── repositories/           # DB 접근 레이어
│       ├── player_repository.py
│       └── ...
│
├── spokes/
│   ├── agents/                 # Policy 기반 (외부 연동)
│   │   ├── player_agent.py
│   │   └── ...
│   └── services/               # Rule 기반 (실제 구현)
│       ├── player_service.py
│       └── ...
│
└── models/
    ├── bases/                  # SQLAlchemy 모델
    └── states/                 # 비어있음 (LangGraph용)
```

### 역할 정의

1. **hub/orchestrators/** - Strategy Pattern 기반 오케스트레이터
   - **역할**: Strategy 판단 → Policy/Rule 분기
   - **특징**: Strategy Pattern 사용
   - **흐름**: Router → Orchestrator → Strategy 판단 → Policy/Rule

2. **spokes/agents/** - Policy 기반 Agent
   - **역할**: 복잡한 비즈니스 로직, ML 모델 사용, 외부 연동
   - **특징**: Policy 기반 처리

3. **spokes/services/** - Rule 기반 Service
   - **역할**: 단순 CRUD 작업, 규칙 기반 처리
   - **특징**: Rule 기반 처리

4. **hub/repositories/** - DB 접근 레이어
   - **역할**: 데이터베이스 접근
   - **특징**: Service가 Repository를 호출

5. **models/states/** - LangGraph 상태 스키마
   - **역할**: LangGraph StateGraph의 상태 정의
   - **현재**: 비어있음 (LangGraph 전환 시 필요)

6. **models/bases/** - SQLAlchemy 모델
   - **역할**: 데이터베이스 모델 정의

### 1. hub/orchestrators/ (Strategy Pattern 기반 오케스트레이터)

#### 강사님 구조
- **위치**: `app/domain/v10/soccer/hub/orchestrators/`
- **파일**: `player_orchestrator.py`, `team_orchestrator.py` 등
- **역할**: Strategy 판단 → Policy/Rule 분기
- **특징**: Strategy Pattern 사용

#### 현재 프로젝트
- **위치**: `app/core/orchestration/workflow_manager.py`
- **파일**: `workflow_manager.py` (중앙 오케스트레이터)
- **역할**: ✅ **동일** - Strategy 판단 → Policy/Rule 분기
- **특징**: ✅ **동일** - Strategy Pattern 사용 (PolicyStrategy, RuleStrategy)
- **추가**: `decision_maker.py` - 정책/규칙 판단 로직 분리

**매핑 결과**: ✅ **완벽히 일치**

```python
# 강사님 구조 (예상)
class PlayerOrchestrator:
    def process(self, request):
        strategy = self._determine_strategy(request)
        if strategy == "policy":
            return self.policy_strategy.process(request)
        else:
            return self.rule_strategy.process(request)

# 현재 프로젝트
class WorkflowManager:
    async def process_request(self, domain, action, request):
        strategy_type = await self.decision_maker.determine_strategy(...)
        strategy = self.strategies.get(strategy_type)
        return await strategy.route(...)
```

## 🎯 LangGraph 전환 전략 적용 가능성

### ✅ 적용 가능한 부분

1. **Orchestrator 전환**
   - `app/core/orchestration/workflow_manager.py` → LangGraph StateGraph로 전환
   - Strategy Pattern 제거
   - 노드 함수로 전환

2. **Agent/Service 유지**
   - `app/domain/reasoning/agents/` - 그대로 유지 (노드에서 호출)
   - `app/domain/*/services.py` - 그대로 유지 (노드에서 호출)

3. **Repository 유지**
   - `app/domain/*/repositories.py` - 그대로 유지
   - Service가 Repository를 호출하는 구조 유지

### ❌ 추가 작업 필요

1. **상태 스키마 정의**
   - `app/core/orchestration/models/states/` 디렉토리 생성
   - `base_state.py`, `workflow_state.py` 등 생성

2. **LangGraph 노드 구현**
   - `app/core/orchestration/nodes.py` 생성
   - 노드 함수 구현

3. **LangGraph 그래프 빌드**
   - `app/core/orchestration/graph.py` 생성
   - 그래프 빌드 함수 구현

## 🔍 추가 발견 사항

### 현재 프로젝트의 추가 구조

1. **ReasoningHub** (`app/domain/reasoning/orchestrators/reasoning_hub.py`)

   - **특징**: 휴리스틱 기반 판단
   - **강사님 구조와의 관계**: Orchestrator 내부의 판단 로직을 분리한 구조
   - **LangGraph 전환 시**: `determine_strategy_node`에서 DecisionMaker 사용

## ✅ 결론

### 역할 매핑 결과

**✅ 대부분의 역할이 완벽히 일치합니다**

1. **Orchestrator**: ✅ Strategy Pattern 사용, Policy/Rule 분기
2. **Agent**: ✅ Policy 기반, 복잡한 비즈니스 로직
3. **Service**: ✅ Rule 기반, 단순 CRUD 작업
4. **Repository**: ✅ DB 접근 레이어
5. **Models**: ✅ SQLAlchemy 모델 (구조만 다름)
6. **States**: ❌ 미구현 (LangGraph 전환 시 필요)

### LangGraph 전환 전략 적용 가능성

**✅ 강사님의 전환 전략을 그대로 적용할 수 있습니다**

**이유**:
1. 핵심 역할이 모두 일치함
2. 구조만 다를 뿐 의도와 역할이 동일함
3. LangGraph 전환 시 필요한 작업이 명확함

**필요한 작업**:
1. 상태 스키마 정의 (`models/states/`)
2. LangGraph 노드 구현 (`nodes.py`)
3. LangGraph 그래프 빌드 (`graph.py`)
4. WorkflowManager 전환
