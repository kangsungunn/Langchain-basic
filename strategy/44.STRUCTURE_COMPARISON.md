# 기존 vs 새로운 구조 비교 분석

> **목적**: 어떤 구조가 민사소송법 답안지 첨삭 시스템에 더 적합한지 판단

---

## 📊 현재 상황 분석

### 기존 구조 현황

```
app/domain/
├── admin/
│   ├── agents/                    # 이미 있음!
│   │   ├── feedback_agent.py     # ✅ 새 구조와 유사
│   │   ├── reasoning_agent.py    # ✅ 새 구조와 유사
│   │   ├── reference_agent.py    # ✅ 새 구조와 유사
│   │   └── submission_agent.py   # ✅ 새 구조와 유사
│   │
│   ├── orchestrators/
│   │   ├── _flow.py              # ExaminationOrchestrator (특허 심사)
│   │   ├── patent_flow.py        # PatentOrchestrator
│   │   └── trademark_flow.py     # TrademarkOrchestrator
│   │
│   ├── services/
│   │   ├── examination_service.py
│   │   ├── patent_service.py
│   │   └── trademark_service.py
│   │
│   └── bases/
│       ├── reference_reasoning.py
│       ├── submission_reasoning.py
│       └── reasoning_feedback.py
│
├── examination/
├── patent/
└── trademark/
```

**핵심 발견**:
- ✅ `admin/agents/` 폴더에 이미 **reference, submission, reasoning, feedback** 에이전트가 존재
- ✅ `admin/bases/` 폴더에 도메인 간 관계 파일 존재
- ⚠️ 하지만 내용이 비어있거나 특허/상표 분석용 코드가 섞여있음

---

## 🔍 상세 비교

### 1️⃣ 목적 적합성

#### 기존 구조의 목적
```
특허/상표 분석 시스템
- 특허법 조문 기반 판단
- 특허 명세서 분석
- 상표 식별력 분석
```

**민사소송법 답안지 첨삭과의 적합도**: ❌ **부적합**

**이유**:
- 특허/상표 도메인 ≠ 답안지 첨삭 도메인
- 조문 기반 판단 ≠ 논점 구조 비교
- 명세서 분석 ≠ 서술형 답안 분석

---

#### 새로운 구조의 목적
```
답안지 첨삭 시스템
- 문제-모범답안 기준
- 논점 구조 비교
- 서술형 답안 분석
- 학습용 피드백
```

**민사소송법 답안지 첨삭과의 적합도**: ✅ **완벽히 적합**

---

### 2️⃣ 코드 재사용 가능성

#### 재사용 가능한 부분 ⭐⭐⭐

| 코드 | 재사용 가능 여부 | 비고 |
|------|------------------|------|
| `orchestrators/` 패턴 | ✅ **가능** | 오케스트레이터 패턴 자체는 동일 |
| `services/` 패턴 | ✅ **가능** | 서비스 레이어 패턴 동일 |
| `agents/` 패턴 | ✅ **가능** | 에이전트 패턴 동일 |
| 모델 로드 로직 | ✅ **가능** | EXAONE 로드 로직 재사용 가능 |
| LangGraph 구조 | ✅ **가능** | 워크플로우 패턴 재사용 가능 |
| MCP 프로토콜 | ✅ **가능** | 도메인 간 통신 패턴 재사용 가능 |

#### 재사용 불가능한 부분 ❌

| 코드 | 재사용 불가 이유 |
|------|------------------|
| `examination_service.py` | 특허법 조문 기반 로직 (≠ 논점 비교) |
| `patent_flow.py` | 특허 명세서 분석 로직 (≠ 답안지 분석) |
| 도메인 모델 | 특허/상표 모델 (≠ 문제/답안 모델) |

### 3️⃣ 마이그레이션 난이도

#### 옵션 A: 기존 구조 유지 + 새 기능 추가

```
app/domain/
├── admin/
│   ├── agents/            # 기존 유지
│   ├── orchestrators/     # 기존 유지
│   ├── services/          # 기존 유지
│   └── bases/             # 기존 유지
│
├── examination/           # 기존 (특허 심사)
├── patent/                # 기존 (특허 분석)
├── trademark/             # 기존 (상표 분석)
│
└── answer_review/         # 신규 (답안지 첨삭) ⭐
    ├── reference/
    ├── submission/
    ├── reasoning/
    └── feedback/
```

**장점**:
- ✅ 기존 코드 보존
- ✅ 점진적 추가 가능
- ✅ 기존 기능 유지

**단점**:
- ❌ 구조 복잡도 증가 (2개 시스템 공존)
- ❌ 혼란 가능성 (특허 vs 답안지)
- ❌ 코드 중복 가능성
- ❌ 유지보수 부담 증가

**마이그레이션 난이도**: 🟢 **쉬움** (새 폴더만 추가)

---

#### 옵션 B: 완전히 새로운 구조로 전환 ⭐ 추천

```
app/domain/
├── reference/             # 신규 (기준 지식)
├── submission/            # 신규 (제출 답안)
├── reasoning/             # 신규 (추론, HUB)
└── feedback/              # 신규 (피드백)
```

**장점**:
- ✅ 깔끔한 구조 (단일 목적)
- ✅ 확장성 높음
- ✅ 유지보수 쉬움
- ✅ 팀원 이해 쉬움
- ✅ 새로운 요구사항에 최적화

**단점**:
- ❌ 기존 코드 폐기
- ❌ 초기 작업량 증가

**마이그레이션 난이도**: 🟡 **중간** (새로 작성하되 패턴은 재사용)

### 4️⃣ 실제 코드 재사용 분석

#### 재사용 가능한 코드 (패턴/로직)

**1. 모델 로드 로직** (90% 재사용 가능):

```python
# 기존 (_flow.py)
def _load_model(self):
    self.tokenizer = AutoTokenizer.from_pretrained(str(self.model_path))
    self.model = AutoModelForSequenceClassification.from_pretrained(
        str(self.model_path)
    )
    self.model.to(self.device)
    self.model.eval()

# 새 구조에서도 거의 동일하게 사용 가능
# → app/core/ml/model_loader.py로 이동하면 완벽
```

**2. 오케스트레이터 패턴** (80% 재사용 가능):

```python
# 기존 패턴
class ExaminationOrchestrator:
    def __init__(self, model_path):
        self._load_model()
        self._initialize_services()

    async def execute_examination(self, type, text, ...):
        if type == "rule_based":
            return await self._execute_rule_based(...)
        elif type == "policy_based":
            return await self._execute_policy_based(...)

# 새 구조에도 동일 패턴 적용 가능
class ReasoningHub:
    def __init__(self):
        self._load_model()
        self._initialize_agents()

    async def execute_reasoning(self, reference, submission):
        # 유사한 패턴
```

**3. LangGraph 워크플로우** (70% 재사용 가능):

```python
# 기존 패턴 (examination_agent.py)
workflow = StateGraph(ExaminationState)
workflow.add_node("analyze", self._analyze_node)
workflow.add_node("reason", self._reason_node)
workflow.add_node("decide", self._decide_node)

# 새 구조에도 유사하게 적용
workflow = StateGraph(ReasoningState)
workflow.add_node("detect_issues", self._detect_issues_node)
workflow.add_node("compare_logic", self._compare_logic_node)
workflow.add_node("evaluate_expression", self._evaluate_expression_node)
```

### 5️⃣ 유지보수성

#### 기존 구조 유지 시

**복잡도**: 🔴 **높음**

```
app/domain/
├── admin/           # 관리자? 뭐하는 폴더?
│   ├── agents/      # 어떤 agents? 특허? 답안지?
│   ├── services/    # examination? patent? answer?
│   └── orchestrators/
│
├── examination/     # 심사? 채점?
├── patent/          # 특허 분석
├── trademark/       # 상표 분석
└── answer_review/   # 답안지 첨삭 (신규)
```

**문제점**:
- ❌ 폴더명만 봐서는 역할 불명확
- ❌ 2개 시스템이 섞여있음
- ❌ 신규 개발자 혼란
- ❌ 코드 찾기 어려움

---

#### 새로운 구조 시

**복잡도**: 🟢 **낮음**

```
app/domain/
├── reference/       # 기준 지식 (명확)
├── submission/      # 제출 답안 (명확)
├── reasoning/       # 추론 (명확)
└── feedback/        # 피드백 (명확)
```

**장점**:
- ✅ 폴더명만 봐도 역할 명확
- ✅ 단일 목적 시스템
- ✅ 신규 개발자 빠른 이해
- ✅ 코드 찾기 쉬움

## 💡 권장 전략: **하이브리드 접근**

### 단계별 마이그레이션

#### Phase 1: 패턴 및 공통 로직 추출 (1-2일)

```
1. 기존 코드에서 재사용 가능한 패턴 추출
   - 모델 로드 로직 → app/core/ml/model_loader.py
   - 오케스트레이터 패턴 → app/core/orchestration/base_orchestrator.py
   - LangGraph 템플릿 → 템플릿 파일

2. 기존 폴더를 _legacy/ 폴더로 이동 (보존)
   app/domain/_legacy/
   ├── admin/
   ├── examination/
   ├── patent/
   └── trademark/
```

**장점**:
- ✅ 기존 코드 보존 (참고 가능)
- ✅ 패턴 재사용 가능
- ✅ 롤백 가능

---

#### Phase 2: 새 구조 구축 (3-5일)

```
1. 빈 폴더/파일 생성 (PowerShell 스크립트)
2. 핵심 파일부터 작성
   - MCP 프로토콜
   - 모델 로더
   - Reasoning Hub
3. 도메인별 구현
   - Reference → Submission → Reasoning → Feedback
```

---

#### Phase 3: 기능 구현 (1-2주)

```
1. Phase 1 MVP
   - 1개 문제, 1개 답안
   - 기본 논점 비교
   - 간단한 피드백

2. Phase 2 확장
   - 반자동 논점 추출
   - OCR 추가
   - 고급 피드백
```

---

#### Phase 4: _legacy/ 폴더 삭제 (나중)

```
새 구조가 안정되면 삭제
```
