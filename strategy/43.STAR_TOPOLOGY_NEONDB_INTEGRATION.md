## 현재 진행 상황

### ✅ 완료된 작업

1. **데이터 준비 단계**
   - 특허법 조문 파싱 및 JSONL 변환
   - 학습 데이터 분할 (train/val/test)

2. **모델 학습 단계**
   - KoELECTRA: 특허법 조문 학습 완료 (Gateway 모델)
   - EXAONE 2.4B: LoRA 학습 완료 (Star Node 모델)

3. **데이터베이스 설계 단계**
   - 교차 엔티티 테이블 DDL 작성
   - PGVector 임베딩 테이블 설계

### 🔄 현재 단계: **NeonDB 연결 및 통합**

EXAONE (Star Node)과 NeonDB를 연결하여:
- 사용자 입력/출력 기록 저장
- 벡터 임베딩 저장 (RAG)
- 케이스 이력 관리
- 학습된 지식 영구 저장

## NeonDB의 역할

### 1. 영구 저장소 (Persistent Storage)

```
┌─────────────────────────────────────────┐
│           NeonDB (PostgreSQL)           │
├─────────────────────────────────────────┤
│                                         │
│ 1️⃣ 입력/출력 기록                       │
│    examination_document                 │
│    ├─ 사용자 질문                        │
│    ├─ AI 응답                           │
│    ├─ 메타데이터 (생성 시각, 버전 등)    │
│    └─ 품질 점수                         │
│                                         │
│ 2️⃣ 벡터 임베딩 (RAG)                    │
│    examination_document_embeddings      │
│    ├─ 텍스트 → 벡터 변환                 │
│    ├─ 유사도 검색 (PGVector)             │
│    └─ 컨텍스트 검색 속도 향상            │
│                                         │
│ 3️⃣ 도메인 관계 추적                     │
│    examination_dispute                  │
│    ├─ 심사 → 분쟁 흐름 추적              │
│    └─ 케이스 연관성 파악                 │
│                                         │
│ 4️⃣ 분쟁-문서 관계                       │
│    dispute_document                     │
│    ├─ 분쟁 대응 문서 생성 이력           │
│    └─ 전략 및 결과 추적                  │
└─────────────────────────────────────────┘
```

### 2. RAG (Retrieval-Augmented Generation) 지원

```
┌──────────────────────────────────────────────────────────┐
│                  RAG 워크플로우                           │
└──────────────────────────────────────────────────────────┘

[사용자 질문]
   "이 발명은 신규성이 있나요?"
      ↓
[1] 질문 임베딩
   OpenAI Embeddings API
   └─ "이 발명은..." → [0.234, -0.123, 0.456, ...]

[2] 유사도 검색 (PGVector)
   SELECT
       content,
       embedding <=> %s as distance
   FROM examination_document_embeddings
   ORDER BY embedding <=> %s
   LIMIT 5;

   결과:
   ├─ 과거 유사 케이스 3개
   ├─ 관련 법조문 2개
   └─ 관련 판례 1개

[3] 컨텍스트 구성
   프롬프트 = f"""
   [관련 케이스]
   {유사_케이스_1}
   {유사_케이스_2}

   [관련 법조문]
   {특허법_제29조}

   [사용자 질문]
   {질문}

   위 컨텍스트를 참고하여 판단하세요.
   """

[4] EXAONE 추론
   EXAONE + LoRA
   └─ 컨텍스트 + 학습된 지식 → 판단

[5] 응답 저장 및 임베딩
   1. examination_document ← 응답 저장
   2. examination_document_embeddings ← 응답 임베딩 저장
      └─ 향후 RAG 컨텍스트로 재사용
```

## 현재 단계의 의미

### 🎯 현재 작업: "NeonDB 연결 및 테이블 생성"

```
전체 프로젝트 진행도:
[████████████░░░░░░░░░░░░░░░] 60%

├─ ✅ 데이터 준비          (100%)
├─ ✅ KoELECTRA 학습       (100%)
├─ ✅ EXAONE LoRA 학습     (100%)
├─ 🔄 NeonDB 통합          (60%)  ← 현재 여기
│   ├─ ✅ DDL 작성         (100%)
│   ├─ 🔄 연결 설정        (80%)
│   └─ ⏳ 테이블 생성      (진행 중)
├─ ⏳ 모델 로더 구현       (0%)

└─ ⏳ 오케스트레이터       (0%)
```

### 왜 NeonDB 연결이 중요한가?

1. **학습된 지식의 영구 저장**
   - KoELECTRA, EXAONE이 학습한 내용은 모델 파라미터에 저장됨
   - 하지만 실행 시 사용자 입력/출력은 휘발성 (재시작 시 사라짐)
   - NeonDB에 저장하여 영구 보존

2. **RAG를 통한 성능 향상**
   - 학습 데이터: 831개 조문 (정적)
   - 실행 데이터: 사용자 질문/응답 누적 (동적)
   - PGVector로 유사 케이스 검색 → 더 정확한 판단

3. **케이스 이력 관리**
   - 심사 → 분쟁 흐름 추적

## 학습된 데이터의 흐름 (상세)

### 학습 시: 데이터 → 모델 파라미터

```
┌──────────────────────────────────────────────────────────┐
│              학습 시 데이터 흐름                          │
└──────────────────────────────────────────────────────────┘

[입력 데이터]
   data/processed/patent/train.jsonl
   {
     "input": "제29조",
     "output": "특허를 받을 수 있는 발명은 산업상 이용할 수 있는..."
   }

      ↓ Tokenization

   [1, 234, 567, 89, ...] (토큰 ID)

      ↓ Forward Pass

   ┌─────────────────────┐
   │   모델 (가중치)      │ ← 초기: 랜덤 가중치
   │   W1, W2, W3, ...   │
   └─────────────────────┘

      ↓ Loss 계산

   예측: "특허를 받을 수 있는 발명은..."
   정답: "특허를 받을 수 있는 발명은 산업상 이용할 수 있는..."
   Loss = CrossEntropy(예측, 정답)

      ↓ Backward Pass (Gradient)

   dL/dW1, dL/dW2, dL/dW3, ...

      ↓ Update (Optimizer)

   ┌─────────────────────┐
   │   모델 (가중치)      │ ← 업데이트된 가중치
   │   W1', W2', W3', ...│    (학습된 지식 저장)
   └─────────────────────┘

      ↓ 반복 (Epoch 1, 2, 3)

   ┌─────────────────────┐
   │ 최종 학습된 모델     │ ← artifacts/models/finetuned/
   │  └─ 특허법 지식이    │
   │     가중치에 인코딩됨 │
   └─────────────────────┘
```

### 실행 시: 모델 파라미터 + NeonDB 컨  텍스트

```
┌──────────────────────────────────────────────────────────┐
│             실행 시 데이터 흐름                           │
└──────────────────────────────────────────────────────────┘

[사용자 입력]
   "이 발명은 신규성이 있나요? (발명 설명...)"

      ↓ (A) 모델 로드

   ┌─────────────────────────────────┐
   │ artifacts/models/finetuned/     │
   │ └─ exaone/lora/                 │
   │    └─ adapter_model.safetensors │ ← 학습된 가중치
   └─────────────────────────────────┘
              ↓ Load
   ┌─────────────────────────────────┐
   │ EXAONE + LoRA (메모리)           │
   │ W1', W2', W3', ...              │ ← 특허법 지식이 담긴 가중치
   └─────────────────────────────────┘

      ↓ (B) 컨텍스트 검색 (NeonDB RAG)

   [질문 임베딩]
   "이 발명은 신규성이..." → [0.234, -0.123, ...]

      ↓ PGVector 유사도 검색

   ┌─────────────────────────────────┐
   │ NeonDB PGVector                 │
   │ examination_document_embeddings │
   │                                 │
   │ SELECT content, embedding       │
   │ FROM examination_document_      │
   │      embeddings                 │
   │ ORDER BY embedding <=>          │
   │          '[0.234, -0.123, ...]' │
   │ LIMIT 5;                        │
   └─────────────────────────────────┘

      ↓ 검색 결과

   [컨텍스트]
   ├─ 과거 유사 케이스 1: "발명 A는 신규성이 인정됨 (특허법 제29조)"
   ├─ 과거 유사 케이스 2: "발명 B는 선행기술과 유사하여 거절"
   └─ 관련 조문: "제29조 제1항: 산업상 이용할 수 있는 발명..."

      ↓ (C) LLM 추론

   프롬프트 = f"""
   당신은 특허 심사관입니다. 다음 정보를 참고하여 판단하세요:

   [관련 과거 케이스]
   {컨텍스트}

   [사용자 질문]
   {질문}

   신규성 여부를 판단하고 법적 근거를 제시하세요.
   """

      ↓ EXAONE Forward Pass

   ┌─────────────────────────────────┐
   │ EXAONE + LoRA                   │
   │ 프롬프트 → 토큰화 → 추론         │
   │                                 │
   │ 학습된 가중치 + 컨텍스트         │
   │ └─> 법률 판단 생성               │
   └─────────────────────────────────┘

      ↓ 출력

   [AI 응답]
   {
     "judgment": "신규성 있음",
     "confidence": 0.85,
     "legal_grounds": ["특허법 제29조 제1항"],
     "reasoning": "본 발명은 선행기술과 차이가 있으며..."
   }

      ↓ (D) 저장 (NeonDB)

   1. examination_document ← 응답 저장
   2. examination_document_embeddings ← 응답 임베딩 저장
      └─ 향후 다른 케이스의 RAG 컨텍스트로 재사용
```

## NeonDB 연결의 핵심 가치

### 학습 vs 실행 비교

| 구분 | 학습 단계 | 실행 단계 (NeonDB 연결 후) |
|------|-----------|----------------------------|
| **데이터 소스** | 정적 데이터 (831개 조문) | 동적 데이터 (누적되는 케이스) |
| **지식 저장** | 모델 파라미터 | NeonDB + 모델 파라미터 |
| **업데이트** | 재학습 필요 | 자동 누적 (RAG) |
| **컨텍스트** | 학습 데이터만 | 학습 데이터 + 과거 케이스 |
| **성능** | 고정 | 시간이 지날수록 향상 |

# app/core/shared/orchestration/star_node.py

class LegalStarNode:
    def process(self, user_input: str):
        # (1) KoELECTRA 분류
        classification = self.koelectra.classify(user_input)

        # (2) NeonDB RAG
        context = self.neondb.search_similar(user_input)

        # (3) EXAONE 추론
        prompt = f"컨텍스트: {context}\n질문: {user_input}"
        response = self.exaone.generate(prompt)

        # (4) NeonDB 저장
        self.neondb.save(user_input, response)

        return response
```

❌ 판례 정보 활용 불가
❌ 입력/출력 기록 없음 (재시작 시 사라짐)
```

### NeonDB 연결 후 실행하면?

```
[사용자] "이 발명은 신규성이 있나요?"
   ↓ (1) 입력 저장 (NeonDB)
[EXAONE]
   ├─ (2-a) 학습된 지식 (모델 파라미터)
   └─ (2-b) NeonDB RAG
       ├─ 과거 유사 케이스 3개
       ├─ 관련 판례 2개
       └─ 관련 조문 5개
   ↓ 추론
   "본 발명은 과거 케이스 2024-001과 유사하며,
    신규성이 인정될 가능성이 높습니다."
   ↓ (3) 응답 저장 + 임베딩 저장 (NeonDB)

[장점]
✓ 구체적이고 정확한 판단
✓ 과거 케이스 참조 가능
✓ 시간이 지날수록 성능 향상 (케이스 누적)
✓ 영구 기록 (감사 추적 가능)
```

## 핵심 개념 정리

### 1. 학습된 지식 (모델 파라미터)

```
특허법 조문 (831개)
   ↓ 학습
모델 가중치 (W1, W2, ...)
   └─ "제29조는 신규성에 관한 조항이다" 같은 지식이 가중치에 암묵적으로 인코딩됨
```

**특징**:
- 빠름 (메모리에 로드)
- 정적 (재학습 필요)
- 암묵적 (가중치로 인코딩)

### 2. 동적 컨텍스트 (NeonDB RAG)

```
사용자 질문 + AI 응답 (누적)
   ↓ 임베딩
PGVector (examination_document_embeddings)
   └─ 유사도 검색으로 관련 케이스 검색
```

**특징**:
- 느림 (DB 조회)
- 동적 (자동 누적)
- 명시적 (텍스트로 저장)

### 3. 두 가지의 결합

```
[최종 판단] = [학습된 지식] + [동적 컨텍스트]
              (모델 파라미터)   (NeonDB RAG)
```

이것이 바로 **Star Topology + NeonDB** 아키텍처의 핵심입니다.

## 현재 진행 중인 "NeonDB 연결" 단계의 의미

```
전체 프로젝트 타임라인:

Past ──────────> Present ──────────> Future

✅ 학습 완료      🔄 연결 중        ⏳ 실행 예정
(모델 학습)       (DB 통합)        (서비스 런칭)
    │                │                 │
    ├─ 데이터 준비    ├─ NeonDB 설정    ├─ API 서버
    ├─ KoELECTRA     ├─ 테이블 생성    ├─ 오케스트레이터
    └─ EXAONE LoRA   └─ 모델 로더      └─ 프론트엔드
                         ↑
                    현재 위치 ⭐
                    (전체의 60%)
```

**현재 단계는**:
- 학습된 모델(정적)과 실행 환경(동적)을 연결하는 **브릿지**
- 모델의 지식을 실제 서비스로 전환하는 **핵심 단계**
- RAG를 통해 성능을 한 단계 높이는 **차별화 포인트**

3. **최종 목표**: 사용자 입력 → KoELECTRA 분류 → EXAONE 추론(학습된 지식 + NeonDB RAG) → 응답 → NeonDB 저장 → 누적

```
학습 데이터 (정적)          실행 데이터 (동적)

모델 파라미터              NeonDB PGVector
     ↓                           ↓
     └─────> 결합 ◄──────────────┘
              ↓
          더 나은 판단
```

현재 NeonDB 연결 작업은 이 **"결합"을 가능하게 하는 핵심 단계**입니다.
