## NeonDB란?

**NeonDB**는 **서버리스 PostgreSQL 데이터베이스**입니다. 클라우드에서 PostgreSQL을 제공하는 서비스로, 별도의 서버 관리 없이 데이터베이스를 사용할 수 있습니다.

### 특징

- ✅ **서버리스**: 서버 설치/관리 불필요
- ✅ **PostgreSQL 호환**: 표준 PostgreSQL 사용
- ✅ **자동 스케일링**: 트래픽에 따라 자동 확장
- ✅ **무료 티어 제공**: 개발/테스트용으로 충분
- ✅ **빠른 설정**: 몇 분 안에 데이터베이스 생성 가능

---

## 왜 NeonDB를 사용하는가?

### 1. 데이터 영구 저장

**문제**: 애플리케이션을 재시작하면 메모리의 데이터가 사라집니다.

**해결**: NeonDB에 데이터를 저장하면:
- 서버 재시작 후에도 데이터 유지
- 여러 서버 인스턴스가 같은 데이터 공유
- 데이터 백업 및 복구 가능

### 2. 구조화된 데이터 관리

우리 시스템은 다음과 같은 구조화된 데이터를 다룹니다:

```
문제 (Problem)
  └─ 모범 답안 (ReferenceAnswer)
      └─ 쟁점 (Issue)

사용자 답안 (UserAnswer)
  └─ 구조 분석 (AnswerStructure)

추론 작업 (ReasoningTask)
  └─ 추론 결과 (ReasoningResult)

피드백 (Feedback)
  └─ 피드백 항목 (FeedbackItem)
```

이런 **관계형 데이터**를 효율적으로 저장하고 조회하려면 **관계형 데이터베이스(PostgreSQL)**가 필요합니다.

### 3. 동시성 및 성능

- 여러 사용자가 동시에 접근 가능
- 인덱스를 통한 빠른 검색
- 트랜잭션으로 데이터 일관성 보장

## NeonDB의 역할

### 1. 데이터 저장소 (Data Persistence)

```
┌─────────────────┐
│  FastAPI 서버   │
│  (메모리)       │
└────────┬────────┘
         │ SQL 쿼리
         │ (INSERT, SELECT, UPDATE, DELETE)
         ▼
┌─────────────────┐
│   NeonDB        │
│  (디스크 저장)   │
│                 │
│  - problems     │
│  - answers      │
│  - feedbacks    │
└─────────────────┘
```

**역할**: 모든 비즈니스 데이터를 안전하게 저장

### 2. 도메인 간 데이터 공유

우리 시스템은 4개의 도메인으로 구성되어 있습니다:

```
Reference Domain (기준 지식)
    ↓ 문제, 모범답안, 쟁점 제공
Submission Domain (사용자 답안)
    ↓ 답안 제출
Reasoning Domain (추론 엔진)
    ↓ 분석 결과 생성
Feedback Domain (피드백)
    ↓ 최종 피드백 제공
```

**NeonDB의 역할**: 각 도메인이 생성한 데이터를 저장하고, 다른 도메인이 필요할 때 조회할 수 있게 합니다.

### 3. 학습 데이터와 운영 데이터 분리

```
┌─────────────────────────────────────┐
│  학습 데이터 (Training Data)        │
│  - JSONL 파일 (data/processed/)      │
│  - 모델 학습용                       │
└─────────────────────────────────────┘
              ↓ 학습
┌─────────────────────────────────────┐
│  학습된 모델 (Trained Model)         │
│  - artifacts/models/finetuned/       │
│  - EXAONE + LoRA 가중치             │
└─────────────────────────────────────┘
              ↓ 추론
┌─────────────────────────────────────┐
│  운영 데이터 (NeonDB)               │
│  - 사용자 답안                       │
│  - 분석 결과                        │
│  - 피드백                           │
└─────────────────────────────────────┘
```

**핵심**:
- **학습 데이터**: 모델을 학습시키기 위한 정적 데이터 (JSONL 파일)
- **운영 데이터**: 실제 사용자가 제출한 답안과 분석 결과 (NeonDB)

## 데이터 흐름 이해

### 전체 데이터 흐름도

```
[사용자]
  │
  │ 1. 답안 제출
  ▼
[Submission Domain]
  │ POST /api/v1/submission/answers/text
  │ { "problem_id": "...", "content": "..." }
  │
  │ 2. 데이터베이스 저장
  ▼
[NeonDB - user_answers 테이블]
  │
  │ 3. 구조 분석 요청
  ▼
[Submission Domain - 구조 분석]
  │ POST /api/v1/submission/answers/{id}/analyze
  │
  │ 4. 구조 분석 결과 저장
  ▼
[NeonDB - answer_structures 테이블]
  │
  │ 5. 추론 분석 요청
  ▼
[Reasoning Domain]
  │ POST /api/v1/reasoning/analyze/issues
  │
  │ 6. EXAONE 모델 추론 (현재는 더미)
  │    - 문제, 모범답안, 사용자답안 비교
  │    - 쟁점 포함률, 논리성, 표현력 분석
  │
  │ 7. 분석 결과 저장
  ▼
[NeonDB - reasoning_tasks, reasoning_results 테이블]
  │
  │ 8. 피드백 생성 요청
  ▼
[Feedback Domain]
  │ POST /api/v1/feedback/generate
  │
  │ 9. 추론 결과를 기반으로 피드백 생성
  │    - 강점/약점 분석
  │    - 개선 제안 생성
  │
  │ 10. 피드백 저장
  ▼
[NeonDB - feedbacks, feedback_items 테이블]
  │
  │ 11. 피드백 반환
  ▼
[사용자]
```

### 학습 데이터와 운영 데이터의 관계

#### 학습 단계 (Training Phase)

```
1. 학습 데이터 준비
   data/processed/civil_law/train_samples.jsonl
   ├─ 문제
   ├─ 모범답안
   ├─ 사용자답안
   └─ 라벨 (정답)

2. 모델 학습
   python training/examination/civil_law/train_simple.py
   ├─ EXAONE 모델 로드
   ├─ LoRA 적용
   └─ 학습 실행

3. 모델 저장
   artifacts/models/finetuned/legal/final_simple/
   └─ LoRA 가중치 저장
```

#### 운영 단계 (Inference Phase)

```
1. 사용자 답안 제출
   → NeonDB에 저장 (user_answers 테이블)

2. 모델 추론
   → 학습된 모델 로드
   → 문제 + 모범답안 + 사용자답안 입력
   → 분석 결과 출력

3. 결과 저장
   → NeonDB에 저장 (reasoning_results 테이블)

4. 피드백 생성
   → 분석 결과를 기반으로 피드백 생성
   → NeonDB에 저장 (feedbacks 테이블)
```

**핵심 차이점**:
- **학습 데이터**: 모델을 가르치기 위한 교재 (정적)
- **운영 데이터**: 실제 사용자의 답안과 분석 결과 (동적)

## 연동 과정 및 에러 해결

### Step 1: NeonDB 프로젝트 생성

**목적**: 클라우드에 PostgreSQL 데이터베이스 인스턴스 생성

**과정**:
1. https://console.neon.tech 접속
2. 프로젝트 생성
3. Connection String 복사

**결과**: `postgresql://username:password@host/dbname?sslmode=require` 형태의 URL 획득

---

### Step 2: DATABASE_URL 설정

**목적**: 애플리케이션이 데이터베이스에 연결할 수 있도록 URL 설정

**과정**:
1. `.env` 파일에 `DATABASE_URL` 추가
2. **중요**: `postgresql://` → `postgresql+asyncpg://`로 변경
   - 이유: FastAPI는 비동기 라이브러리(asyncpg)를 사용하므로

**형식**:
```bash
DATABASE_URL=postgresql+asyncpg://user:pass@host/dbname?sslmode=require
```

---

### Step 3: Alembic 초기화

**목적**: 데이터베이스 스키마(테이블 구조)를 버전 관리하고 자동으로 생성

**명령어**:
```bash
alembic init database/migrations
```

**역할**:
- `alembic.ini`: Alembic 설정 파일
- `database/migrations/env.py`: 마이그레이션 실행 환경
- `database/migrations/versions/`: 마이그레이션 스크립트 저장소

**결과**: 마이그레이션 관리 시스템 생성

---

### Step 4: 마이그레이션 생성

**목적**: SQLAlchemy 모델을 기반으로 데이터베이스 테이블 생성 SQL 자동 생성

**명령어**:
```bash
alembic revision --autogenerate -m "Initial migration - all domains"
```

**작동 원리**:
1. SQLAlchemy 모델 스캔 (`app/domain/*/models.py`)
2. 현재 데이터베이스 스키마와 비교
3. 차이점을 마이그레이션 스크립트로 생성

**결과**: `database/migrations/versions/xxxxx_initial_migration.py` 파일 생성

---

### Step 5: 마이그레이션 적용

**목적**: 생성된 마이그레이션 스크립트를 실행하여 실제 데이터베이스에 테이블 생성

**명령어**:
```bash
alembic upgrade head
```

**작동 원리**:
1. `alembic_version` 테이블 확인 (현재 적용된 버전)
2. 미적용 마이그레이션 찾기
3. 순차적으로 마이그레이션 실행
4. `alembic_version` 테이블 업데이트

**결과**: 데이터베이스에 모든 테이블 생성

---

### Step 6: 시딩 (Seeding)

**목적**: 개발/테스트를 위한 초기 데이터 삽입

**명령어**:
```bash
python database/seed_data.py
```

**역할**:
- 테스트용 문제, 모범답안, 쟁점 데이터 삽입
- API 테스트 시 실제 데이터로 확인 가능

## 주요 에러 및 해결

### 에러 1: `UnicodeDecodeError: 'cp949' codec can't decode`

**원인**: Windows에서 한글 주석이 포함된 파일을 읽을 때 인코딩 문제

**해결**:
- `alembic.ini`와 `env.py`의 한글 주석을 영어로 변경
- 파일 인코딩을 UTF-8로 저장

**수정 파일**:
- `alembic.ini`
- `database/migrations/env.py`

---

### 에러 2: `TypeError: connect() got an unexpected keyword argument 'sslmode'`

**원인**: asyncpg 드라이버는 `sslmode` 파라미터를 지원하지 않음

**해결**:
- URL에서 모든 쿼리 파라미터 제거
- `connect_args={'ssl': True}`로 SSL 설정

**수정 위치**: `app/core/database/connection.py`

```python
# URL에서 쿼리 파라미터 제거
clean_url = urlunparse((
    parsed.scheme,
    parsed.netloc,
    parsed.path,
    parsed.params,
    '',  # 모든 쿼리 파라미터 제거
    parsed.fragment
))

# SSL 설정
if 'sslmode=require' in database_url:
    connect_args['ssl'] = True
```

---

### 에러 3: `NoForeignKeysError: Could not determine join condition`

**원인**: SQLAlchemy 관계(relationship)에서 Foreign Key가 누락됨

**해결**:
- `ReasoningResult.task_id`에 `ForeignKey("reasoning_tasks.id")` 추가
- 양방향 관계 설정 (`back_populates`)

**수정 위치**: `app/domain/reasoning/models.py`

```python
# Before
task_id = Column(String(36), nullable=False, index=True)

# After
task_id = Column(String(36), ForeignKey("reasoning_tasks.id"), nullable=False, index=True)
task = relationship("ReasoningTask", back_populates="results")
```

---

### 에러 4: `MissingGreenlet: greenlet_spawn has not been called`

**원인**: 비동기 세션에서 lazy loading 시도

**해결**:
- Eager loading 사용 (`selectinload`)
- 중첩된 관계도 모두 로드

**수정 위치**: `app/domain/reference/repositories.py`

```python
# Before
.options(selectinload(Problem.reference_answers))

# After
.options(
    selectinload(Problem.reference_answers).selectinload(ReferenceAnswer.issues)
)
```

## 주요 명령어 설명

### `alembic init database/migrations`

**역할**: Alembic 마이그레이션 시스템 초기화

**생성되는 것**:
- `alembic.ini`: 설정 파일
- `database/migrations/env.py`: 마이그레이션 실행 환경
- `database/migrations/versions/`: 마이그레이션 스크립트 폴더

**비유**: Git의 `.git` 폴더처럼, 마이그레이션 버전을 관리하는 시스템

---

### `alembic revision --autogenerate -m "메시지"`

**역할**: 현재 모델과 데이터베이스의 차이를 감지하여 마이그레이션 스크립트 자동 생성

**작동 과정**:
1. SQLAlchemy 모델 스캔
2. 데이터베이스 현재 상태 확인
3. 차이점 감지 (새 테이블, 컬럼 추가/삭제 등)
4. 마이그레이션 파일 생성

**비유**: Git의 `git diff`처럼 차이를 찾아서 변경사항 파일 생성

**예시**:
```bash
alembic revision --autogenerate -m "Add foreign key to reasoning_results"
# → reasoning_results 테이블에 Foreign Key 추가하는 마이그레이션 생성
```

---

### `alembic upgrade head`

**역할**: 모든 미적용 마이그레이션을 순차적으로 실행

**작동 과정**:
1. `alembic_version` 테이블에서 현재 버전 확인
2. `head`(최신 버전)까지의 모든 마이그레이션 찾기
3. 순차적으로 실행 (각 마이그레이션의 `upgrade()` 함수 호출)
4. `alembic_version` 테이블 업데이트

**비유**: Git의 `git pull`처럼 최신 변경사항을 적용

**결과**: 데이터베이스 스키마가 최신 상태로 업데이트됨

---

### `alembic current`

**역할**: 현재 적용된 마이그레이션 버전 확인

**출력 예시**:
```
e33aa43c4583 (head)
```

**용도**:
- 어떤 마이그레이션이 적용되었는지 확인
- 문제 발생 시 디버깅

---

### `alembic downgrade -1`

**역할**: 마지막 마이그레이션을 롤백 (되돌리기)

**용도**:
- 잘못된 마이그레이션 실행 시 되돌리기
- 테스트 목적

**주의**: 운영 환경에서는 신중하게 사용

## 데이터베이스 스키마 구조

### 테이블 관계도

```
problems (문제)
  ├─ id (PK)
  └─ reference_answers (1:N)
      ├─ id (PK)
      ├─ problem_id (FK → problems.id)
      └─ issues (1:N)
          ├─ id (PK)
          └─ reference_answer_id (FK → reference_answers.id)

user_answers (사용자 답안)
  ├─ id (PK)
  ├─ problem_id (참조)
  └─ answer_structures (1:1)
      ├─ id (PK)
      └─ user_answer_id (FK → user_answers.id, UNIQUE)

reasoning_tasks (추론 작업)
  ├─ id (PK)
  ├─ user_answer_id (참조)
  └─ reasoning_results (1:N)
      ├─ id (PK)
      └─ task_id (FK → reasoning_tasks.id)

feedbacks (피드백)
  ├─ id (PK)
  ├─ user_answer_id (참조)
  └─ feedback_items (1:N)
      ├─ id (PK)
      └─ feedback_id (FK → feedbacks.id)
```

## 왜 이렇게 복잡한가?

### 1. 도메인 분리 (Domain-Driven Design)

각 도메인은 독립적으로 데이터를 관리합니다:
- **Reference Domain**: 문제, 모범답안, 쟁점
- **Submission Domain**: 사용자 답안, 구조 분석
- **Reasoning Domain**: 추론 작업, 분석 결과
- **Feedback Domain**: 피드백, 피드백 항목

**이점**:
- 각 도메인을 독립적으로 개발/테스트 가능
- 변경 사항이 다른 도메인에 영향 최소화

### 2. 관계형 데이터베이스의 장점

**Foreign Key 제약조건**:
- 데이터 무결성 보장
- 잘못된 데이터 삽입 방지
- 관련 데이터 자동 삭제 (CASCADE)

**예시**:
```python
# 문제 삭제 시
problem.delete()
# → 자동으로 모범 답안 삭제 (CASCADE)
# → 자동으로 쟁점 삭제 (CASCADE)
```

## 학습 데이터 vs 운영 데이터

### 학습 데이터 (Training Data)

**위치**: `data/processed/civil_law/train_samples.jsonl`

**형태**: JSONL 파일 (각 줄이 하나의 JSON 객체)

**용도**:
- 모델 학습 (EXAONE + LoRA)
- 정적 데이터 (변경되지 않음)

**예시** (JSONL 형식):
```jsonl
{"id": 1001, "problem": "...", "reference_answer": "...", "user_answer": "...", "labels": {"issue_coverage": 0.85, "logic_score": 0.75, "expression_score": 0.80}}
{"id": 1002, "problem": "...", ...}
```

---

### 운영 데이터 (Operational Data)

**위치**: NeonDB

**형태**: 관계형 데이터베이스 테이블

**용도**:
- 실제 사용자 답안 저장
- 분석 결과 저장
- 피드백 저장
- 동적 데이터 (계속 추가됨)

**예시**:
```sql
-- 사용자 답안
INSERT INTO user_answers (id, problem_id, content)
VALUES ('user-001', 'prob-seed-001', '...');

-- 분석 결과
INSERT INTO reasoning_results (id, task_id, content, confidence)
VALUES ('result-001', 'task-001', '{"issue_coverage": 0.85}', 0.92);
```

```

  ↓

  ↓

  ↓
NeonDB 저장 (reasoning_results)
  ↓

  ↓
NeonDB 저장 (feedbacks)
  ↓
사용자에게 반환
```

## FAQ

### Q1: 왜 로컬 PostgreSQL 대신 NeonDB를 사용하나요?

**A**:
- 서버 설정 불필요 (서버리스)
- 자동 백업 및 복구
- 여러 환경에서 동일한 데이터베이스 공유 가능
- 무료 티어로 개발/테스트 가능

### Q2: 학습 데이터는 왜 JSONL 파일인가요?

**A**:
- 학습은 일회성 작업 (모델 학습 시에만 사용)
- 대량의 데이터를 빠르게 읽기 위해 JSONL 사용 (스트리밍 처리 가능)
- 각 줄이 하나의 샘플로 구성되어 메모리 효율적
- HuggingFace Datasets 라이브러리와 호환
- 운영 데이터와 분리하여 관리 용이

### Q3: 마이그레이션이 뭔가요?

**A**:
- 데이터베이스 스키마 변경을 버전 관리하는 방법
- Git처럼 변경 이력을 추적
- 팀원들과 스키마 변경사항 공유 가능

### Q4: 시딩이 뭔가요?

**A**:
- 개발/테스트를 위한 초기 데이터 삽입
- 빈 데이터베이스에 샘플 데이터 추가
- API 테스트 시 실제 데이터로 확인 가능
