## 개요

### 목표

**파일만 넣으면 → 자동 학습 → DB 저장 → 첨삭 작업까지 자동화**

```
사용자 파일 입력
    ↓
자동 학습 트리거 (MCP Agent)
    ↓
학습 진행 및 모니터링
    ↓
학습 완료 → 모델 자동 배포
    ↓
NeonDB에 학습 히스토리 저장
    ↓
자동으로 첨삭 작업 수행
```

### 핵심 개념

1. **MCP Agent**: 데이터 변경을 감지하고 자동으로 학습을 시작하는 에이전트
2. **Training Domain**: 학습 데이터, 작업, 모델 버전을 관리하는 도메인
3. **Mixin 패턴**: 코드 재사용을 위한 공통 기능 주입 패턴

## ML 모델 연동

### 1. LoRA (Low-Rank Adaptation)란?

**문제**: 대형 모델(EXAONE 2.4B)을 전체 학습하면 메모리가 부족합니다.

**해결**: LoRA는 모델의 일부만 학습하는 효율적인 방법입니다.

```
전체 모델 학습 (Full Fine-tuning)
┌─────────────────────────────┐
│  EXAONE 2.4B (전체 가중치)   │  ← 2.4B개 파라미터 모두 학습
│  [████████████████████]     │  ← GPU 메모리 부족!
└─────────────────────────────┘

LoRA 학습 (Parameter-Efficient)
┌─────────────────────────────┐
│  EXAONE 2.4B (고정)         │  ← Base 모델은 그대로
│  [████████████████████]     │
└─────────────────────────────┘
         +
┌─────────────────────────────┐
│  LoRA 어댑터 (작은 가중치)   │  ← 0.1%만 학습 (메모리 절약!)
│  [██]                       │
└─────────────────────────────┘
```

**비유**:
- 전체 학습 = 집 전체를 리모델링 (비용 큼)
- LoRA = 작은 증축만 추가 (비용 적음, 효과는 비슷)

### 2. 모델 구조

```
artifacts/models/
├── base/
│   └── exaone-2.4b/          # Base 모델 (고정)
│       ├── config.json
│       ├── pytorch_model.bin
│       └── tokenizer.json
│
└── finetuned/
    └── legal/
        └── final_simple/      # LoRA 어댑터 (학습됨)
            ├── adapter_config.json
            ├── adapter_model.safetensors  ← 학습된 가중치
            └── tokenizer.json
```

**사용 시**: Base 모델 + LoRA 어댑터를 합쳐서 사용

### 3. ModelLoader 구조

```python
# app/core/ml/model_loader.py

class ModelLoader:
    """모델 로더 (싱글톤)"""

    def load(self):
        # 1. LoRA 어댑터 경로 확인
        if adapter_exists:
            # 2. Base 모델 로드
            base_model = load_base_model()
            # 3. LoRA 어댑터 적용
            model = PeftModel.from_pretrained(base_model, adapter_path)
        else:
            # 전체 모델 로드
            model = load_full_model()
```

**싱글톤 패턴**:
- 한 번만 로드하고 재사용
- 메모리 효율적
- 여러 요청이 같은 모델 공유

### 4. 실제 추론 흐름

```
API 요청: POST /api/v1/reasoning/analyze/issues
    ↓
ReasoningEngine.analyze_issues()
    ↓
1. 데이터 로드 (문제, 모범답안, 사용자답안)
    ↓
2. 입력 텍스트 구성
   "[문제] {problem}
    [모범답안] {reference}
    [사용자답안] {user_answer}"

    ↓
4. 결과 변환
   class 0 → coverage_rate 0.3 (낮음)
   class 1 → coverage_rate 0.6 (중간)
   class 2 → coverage_rate 0.9 (높음)
    ↓
5. DB 저장 및 응답
```

## Training Domain 구조

### 1. 도메인 개요

**목적**: 학습 데이터와 모델 학습 작업을 자동으로 관리

```
Training Domain
├── TrainingData      # 학습 데이터 (문제, 답안, 라벨)
├── TrainingJob       # 학습 작업 (진행 상황, 결과)
└── ModelVersion      # 모델 버전 (버전 관리, 성능 메트릭)
```

### 2. 데이터 모델 관계

```
┌─────────────────┐
│ TrainingData    │  ← 학습할 데이터
│ - problem_text  │
│ - reference_... │
│ - user_...      │
│ - labels        │
│ - status        │
└────────┬────────┘
         │ 사용됨
         ▼
┌─────────────────┐
│ TrainingJob     │  ← 학습 작업
│ - job_name      │
│ - status        │
│ - progress      │
│ - metrics       │
│ - model_path    │
└────────┬────────┘
         │ 생성함
         ▼
┌─────────────────┐
│ ModelVersion    │  ← 학습된 모델
│ - version       │
│ - model_path    │
│ - metrics       │
│ - is_active     │
└─────────────────┘
```

### 3. 자동화 흐름

```
[1] 데이터 입력
POST /api/v1/training/data
{
  "problem_text": "...",
  "reference_answer_text": "...",
  "user_answer_text": "...",
  "labels": {"issue_coverage": 0.75}
}
    ↓
TrainingData 생성 (status=PENDING)
    ↓
[2] 자동 트리거 감지
TrainingOrchestrator.check_auto_training_trigger()
    ↓
PENDING 데이터가 10개 이상?
    ↓ YES
[3] 학습 작업 시작
TrainingOrchestrator.start_training()
    ↓
TrainingJob 생성 (status=PENDING)
    ↓
[4] 백그라운드 학습 실행
_run_training() (비동기)
    ↓
- 학습 데이터 → JSONL 파일 저장
- 학습 스크립트 실행 (subprocess)
- 진행 상황 모니터링
    ↓
[5] 학습 완료
- TrainingJob.status = COMPLETED
- ModelVersion 생성 (version=v1.0.0)
- 모델 파일 저장
    ↓
[6] 자동 배포
- 기존 활성 모델 비활성화
- 새 모델 활성화
- ModelLoader 자동 리로드 (다음 요청 시)
```

### 4. TrainingOrchestrator (MCP Agent)

**역할**: 자동화의 핵심 - 데이터 변경 감지 및 학습 트리거

```python
class TrainingOrchestrator:
    """학습 오케스트레이터 (MCP Agent 역할)"""

    async def check_auto_training_trigger(self, min_data_count=10):
        """자동 학습 트리거 조건 확인"""
        pending_count = await self.data_repo.count(status=PENDING)
        return pending_count >= min_data_count

    async def start_training(self, job_name, config):
        """학습 작업 시작"""
        # 1. PENDING 데이터 수집
        # 2. TrainingJob 생성
        # 3. 백그라운드 학습 시작
        asyncio.create_task(self._run_training(...))
```

**MCP Agent의 의미**:
- **Model Context Protocol**: 도메인 간 통신 프로토콜
- **Agent**: 자동으로 작업을 수행하는 에이전트
- 여기서는 "데이터가 쌓이면 자동으로 학습 시작"하는 에이전트

## Base/Mixin 아키텍처

### 1. 왜 Mixin을 사용하는가?

**문제**: 모든 모델에 `created_at`, `updated_at` 필드를 반복 작성

```python
# 기존 방식 (중복)
class Problem(Base):
    created_at = Column(DateTime, default=datetime.utcnow)
    updated_at = Column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)

class UserAnswer(Base):
    created_at = Column(DateTime, default=datetime.utcnow)
    updated_at = Column(DateTime, default=datetime.utcnow, onupdate=datetime.utcnow)

# ... 13개 모델 모두 반복!
```

**해결**: Mixin으로 공통 기능 주입

```python
# Mixin 정의 (한 번만)
class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(...)
    updated_at: Mapped[datetime] = mapped_column(...)

# 사용 (간단)
class Problem(Base, TimestampMixin):
    # created_at, updated_at 자동 포함!
    pass
```

### 2. Mixin 패턴 이해

**비유**: 레고 블록 조합

```
기본 블록 (Base)
┌─────────┐
│  Base  │
└─────────┘

기능 블록 (Mixin)
┌─────────────┐
│TimestampMixin│  ← 시간 관리 기능
└─────────────┘

조합
┌─────────┐
│  Base  │
└────┬────┘
     │
     + TimestampMixin
     │
     ▼
┌─────────────────┐
│ Problem         │  ← 시간 관리 기능 포함!
│ - id            │
│ - title         │
│ - created_at    │  ← Mixin에서 자동 추가
│ - updated_at    │  ← Mixin에서 자동 추가
└─────────────────┘
```

### 3. 구조 개선 과정

#### Before (기존 구조)

```
app/core/database/
└── connection.py
    └── Base = declarative_base()  # SQLAlchemy 1.x 스타일

모든 모델:
- Column(DateTime, default=datetime.utcnow)  # 반복
- SQLAlchemy 1.x 스타일
```

#### After (개선된 구조)

```
app/core/database/
├── base.py
│   └── Base(DeclarativeBase)  # SQLAlchemy 2.0 스타일
│
├── mixin.py
│   ├── TimestampMixin        # 시간 관리
│   ├── SoftDeleteMixin       # 소프트 삭제
│   └── StatusMixin          # 상태 관리
│
└── connection.py
    └── from base import Base  # Base 재사용

모든 모델:
- class Model(Base, TimestampMixin)  # 간단!
- SQLAlchemy 2.0 스타일 (Mapped 타입)
```

### 4. 장기적 이점

#### 확장성 예시: pgvector 추가

```python
# 나중에 pgvector 추가 시
class VectorMixin:
    embedding: Mapped[Optional[Vector]] = mapped_column(
        Vector(1536), nullable=True
    )

# 모든 모델에 한 줄로 추가
class TrainingData(Base, TimestampMixin, VectorMixin):
    # embedding 자동 포함!
    pass
```

**기존 방식**: 13개 모델 모두 수정 필요
**Mixin 방식**: VectorMixin 하나만 추가

#### 유지보수성

```python
# TimestampMixin 수정 (한 곳만)
class TimestampMixin:
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),  # timezone 추가
        server_default=func.now(),
    )
```

**결과**: 모든 모델에 자동 반영! (13개 모델 모두)

   - PENDING 데이터가 10개 이상이면 자동 학습 시작
   - `auto_trigger` 파라미터로 활성화/비활성화 가능

8. **ModelLoader 자동 리로드**
   - 새 모델 활성화 시 자동으로 리로드
   - `reload()` 메서드로 기존 모델 언로드 후 새 모델 로드
   - 다음 추론 요청부터 새 모델 사용

9. **실시간 진행률 모니터링**
   - `ProgressCallback`으로 epoch별 진행률 파일 저장
   - `_monitor_training_progress()`로 5초마다 DB 업데이트
   - `current_epoch`, `progress`, `loss_history` 실시간 업데이트

10. **학습 완료 후 자동 첨삭** (옵션)
    - `config.auto_feedback=True` 설정 시 자동 실행
    - 학습 데이터 중 ID 참조가 있는 데이터로 새 모델 검증
    - 최대 5개 샘플로 쟁점 분석 및 피드백 생성
    - 백그라운드 실행 (학습 완료 응답 지연 없음)

## 핵심 개념 정리

### 1. LoRA (Low-Rank Adaptation)

**왜 사용?**
- 메모리 절약 (전체 모델의 0.1%만 학습)
- 학습 속도 향상
- 효과는 비슷

**어떻게?**
- Base 모델은 고정
- 작은 어댑터만 학습
- 사용 시 합쳐서 사용

### 2. MCP Agent (TrainingOrchestrator)

**역할**: 자동화의 두뇌
- 데이터 변경 감지
- 학습 조건 확인
- 자동 학습 시작
- 진행 상황 모니터링

### 3. Mixin 패턴

**목적**: 코드 재사용
- 공통 기능을 Mixin으로 분리
- 모델에 선택적으로 주입
- 유지보수 용이

**예시**:
- TimestampMixin → 모든 모델에 시간 관리
- VectorMixin → 나중에 벡터 기능 추가

## FAQ

### Q1: 왜 LoRA를 사용하나요?

**A**: GPU 메모리 부족 문제 해결
- EXAONE 2.4B 전체 학습 → CUDA OOM 에러
- LoRA 사용 → 메모리 절약, 학습 가능

### Q2: 자동화는 어떻게 작동하나요?

**A**: TrainingOrchestrator가 감지
1. 학습 데이터가 10개 이상 쌓임
2. `check_auto_training_trigger()` 호출
3. 조건 만족 시 자동으로 학습 시작
4. 백그라운드에서 실행

### Q3: Mixin을 안 쓰면 안 되나요?

**A**: 가능하지만 비효율적
- 모든 모델에 동일 코드 반복
- 수정 시 13개 파일 모두 변경 필요
- Mixin 사용 시 1개 파일만 수정

### Q4: 나중에 실제 데이터로 재학습하려면?

**A**: 모델 파일만 교체
1. 실제 데이터로 재학습
2. 새 모델을 `artifacts/models/finetuned/legal/`에 저장
3. 코드 변경 없이 자동으로 새 모델 사용
